# GameDev Harness

> 一套**可迁移的游戏设计方法体系**：把"我如何做设计判断"沉淀成可读、可查、可生长的架构，让 AI 助手在**统一的方法与记忆**下陪你做设计——而不是每次都从零开始。

以 AI 做游戏设计的一个常见困境开头：每次对话，助手都像第一次进迷宫——昨天的判断、上个月的复盘、上本书读到的原则，它全不记得；你给它塞的文档越多，它越不知道该用哪条；它给出的建议越来越像"大多数人会说的话"，而不是**你的**判断。

GameDev Harness 的做法是把"方法论"本身工程化：**判断标准**（判据）、**思考动作**（技能原子）、**记忆的来路**（叙事链）、**显式的流程**（白盒流水线）都变成文件——AI 出发时带着这些"起点与方向"，走一步记一步，越用越像你。

## 核心概念（30 秒读懂）

| 概念 | 是什么 | 例子 |
|---|---|---|
| **判据（verdicts）** | 一条可执行的判断标准：内容/依据/适用/反面/有效性记录——不是知识，是岔路口往哪走 | "机制为体验服务：当'这个机制很炫'与'让玩家迷茫'冲突时，炫的让路" |
| **技能原子（atoms）** | 一个可自由排列的思考动作，挂在一个认知原语下（共 10 个原语） | "极端化推演"：数值拉满会怎样？复制 10 张会怎样？ |
| **品类包（packs）** | 按品类编排原子（核心必走/发散随机/休眠）与判据清单 | 解谜包、策略肉鸽包 |
| **白盒流水线（pipelines）** | 显式阶段 + 每步固定产出 + 检查点 + 回顾自检 | 概念 → 初稿 → 攻击性检查 → 减法落定 → 回顾 |
| **叙事链（narrative-chain）** | 记忆流的"来路"：每条记录做了什么/为什么/搁置了什么，可溯源 | "上次否掉 X 方案，因为 Y" |
| **记忆检索** | BM25 字面检索（记忆河），向量轨规划中 | 设计前查"以前怎么想的、踩过什么坑" |

## 项目结构（三个部分，一个产品线）

```
GameDev-Skeleton/                ← 本仓库：框架的开发家（协议/进度/读书手册/历史档案）
├── README.md                     ← 你正在看
├── POSITIONING.md                ← 项目定位与边界（内部权威）
├── FRAMEWORK-MIND.md             ← 心智基线：架构精神/实体矩阵/红线（启动必读）
├── FRAMEWORK-AUDIT.md            ← 框架审计手册：周期性体检（漂移/漏洞/优化，触发时读）
├── FRAMEWORK-LAYERING.md         ← 模式/内容/项目三层：可迁移性判定与现状清单（分发/接入时读）
├── FRAMEWORK-PROGRESS.md         ← 进度与待办（A-H 组）
├── READING-PROTOCOL.md           ← "读书"学习方法执行手册
├── runs/                         ← 框架历史档案（可追溯的实验与演化记录）
├── materials/                    ← 原始资料（视频原文/观点提取等）
├── books/                        ← 成长资料：电子书/读书记录（gitignore，不入库）
└── gamedev-harness-dashboard/    ← DSH 插件：Harness 总控台（面板 + 工具 + API）

~/.gamedev-harness/               ← 方法体系的唯一来源（全局骨架，独立 git）
├── atoms/     10 认知原语 + 技能原子 + 治理规范
├── verdicts/  判据库 + 格式规范
├── packs/     品类技能包
├── pipelines/ 白盒流水线
├── skeleton/  知识骨架三块（机制→效果 / 玩家→体验 / 设计哲学）
├── memory/    叙事链（记忆流）
├── decisions/ 架构决策记录（ADR）
├── projects/  项目注册表（真实游戏项目接入）
└── sources/   外部输入来源注册表（书/文章/讲座/视频）
```

**三产品模型**：DSH（DeepSeek Harness，工程平台：记忆/会话/工具/子代理）是宿主；**框架**是方法体系（纯 Markdown，宿主无关）；**插件**是把框架语义映射为 DSH 工具/API/面板的接驳层（不定义语义，只执行语义）。

## 快速开始

**作为游戏设计师（使用它）：**

1. **接入一个真实项目**：指定项目目录 + 品类（puzzle / strategy-roguelike / 自定义），框架生成运行协议（AGENTS.md）+ 检查点目录 + 全局注册；
2. **开始一次设计**：跟随白盒流水线（阶段 → 检查点 → 回顾 → 回写），每个关键决策挂判据；
3. **让它长成你的**：每轮设计复盘回写叙事链与判据有效性记录；读过的书、认同的观点也能沉淀进来（读书学习法）——积累全是你自己的判断与来路。

**作为框架开发者（迭代它本身）：** 本目录即框架的开发家；协议/进度/决策都在这里，三类变更（协议、契约、内容）按版本纪律提交。

**安装插件**（可选，DSH 环境）：

```bash
dsh plugin --profile web add <path>/gamedev-harness-dashboard
# 或注入器：dev_install_package { "dir": "<path>/gamedev-harness-dashboard" }
```

插件提供：侧边栏「Harness 总控台」（概览/项目/原子/判据/生长）+ 一套 `harness_*` 工具（状态/注入/run 流转/生长/检索）。

**会话启动链（M3′）**：接入框架的工作区（项目根含 `.gamedev-harness.json`）新会话**自动绑定** `harness-project` 预设——运行协议注入候选含 `HARNESS-PROTOCOL.md`（见 `docs/DEVELOPMENT-PLAN.md` 阶段 2），纵向完成 协议→心智→恢复→自检；默认预设保持平台中立 `standard`，非框架项目零感知。显式选择其他预设（如 router-standard）被尊重。

## 成长模式：两条轨

| 轨 | 输入 | 流程 | 产出 |
|---|---|---|---|
| **项目复盘** | 你的真实游戏设计 run | 流水线阶段 → 检查点 → 回顾 → 回写 | 判据/原子/骨架条目（带使用验证） |
| **读书/外部输入** | 书/文章/讲座/视频 | 阅读轮：提取 → 我的看法 → **你的判断** → 沉淀 | 判据/原子/骨架条目（带来源 + 你的圈选） |

**验证通道**（防止"别人的知识污染你的判断"）：技能原子须 3 次真实 run 使用验证转正；判据须可质疑 + ≥1 次 run 挂靠 + 你确认；骨架条目/观点由**用户确认制**转正。沉淀什么都由你圈选——agent 只执行，不替你定义。

## 可迁移性

**内容是你量身定制的，模式可以交给任何人。** 其他游戏设计师拿到这套框架，积累的是**完全不同的**技能原子/电子书/项目记录——"别人拿去的是模式，不是你的答案"。分层判定细则与现状清单见 [FRAMEWORK-LAYERING.md](./FRAMEWORK-LAYERING.md)（模式/内容/项目三层 + 归属判定三问）；模板分发机制在推进中（见 FRAMEWORK-PROGRESS H 组：分层审计已完成，空框架包导出待做）。
